- `/dev/ttyTHS1` 正由 UXRE Agent 獨占，MAV 組不能碰。
- NX UART1 對應 `/dev/ttyTHS0`，但線尾目前未接飛控。
- 現在沒有 `/dev/ttyACM0`，表示 Pixhawk USB 沒接到 NX。
- `eth0` 為 `NO-CARRIER`，目前沒有實體網路連線。
- MAVROS 尚未安裝；`pymavlink 2.4.49` 已可用。
- ROS Foxy 官方 apt 倉庫仍有 ARM64 的 MAVROS 2.4.0。
- eMMC 尚餘 4.1 GB、SD 尚餘 106 GB，安裝空間足夠。

Pixhawk 6C 規格只有 TELEM1/2/3、GPS serial 與 USB，沒有原生 Ethernet。因此外殼 ETH 若能傳 MAVLink，必定經過機體內另一個 serial-to-IP／Wi‑Fi 路由器，不是 Pixhawk Ethernet。[Holybro Pixhawk 6C 規格](https://docs.holybro.com/autopilot/pixhawk-6c/technical-specification)、[PX4 Ethernet 支援清單](https://docs.px4.io/v1.15/en/advanced_config/ethernet_setup)

## 建議的 MAVLink transport 順序

1. USB，最適合第一輪驗證

   - Pixhawk USB 接到 NX 後應出現 `/dev/ttyACM0`。
   - 不占用 TELEM2、不修改 UXRE 參數。
   - 先用 `pymavlink` 唯讀收 HEARTBEAT、SYS_STATUS、AUTOPILOT_VERSION。
   - 通過後再讓 MAVROS 接管 USB。
   - 缺點是 QGC 筆電與 NX 不能同時直接占用同一條 Pixhawk USB。

2. 既有 P450 Wi‑Fi/TCP 路由，最可能是永久方案

   歷史紀錄顯示筆電曾透過 P450 Wi‑Fi + TCP 連到 QGC。根據 Pixhawk 6C 沒有 Ethernet，我推論這很可能是：

   ```text
   Pixhawk TELEM1 → 機載 MAVLink/Wi‑Fi 路由器
                  → TCP 5760 或其他自訂 port
                  → 筆電 QGC
   ```

   若 NX 能透過 ETH 或 Wi‑Fi 存取同一個 router，MAVROS 可直接使用：

   ```text
   tcp://<router-ip>:5760
   ```

   目前阻礙是 `eth0` 沒 carrier，而且尚不知道 QGC 使用的 TCP IP/port。這可能只是機載網路設備目前未由主電池供電。

3. TELEM3→NX UART1，永久硬體備案

   - Pixhawk 6C 有獨立 TELEM3。
   - 可接到 NX UART1 `/dev/ttyTHS0`。
   - 使用 `MAV_2_CONFIG=TELEM3`、`MAV_2_MODE=Onboard` 和對應 `SER_TEL3_BAUD`。
   - 只接 TX、RX、GND，交叉 TX/RX；不可把 Pixhawk 5V 直接送進 NX。
   - 目前 `/dev/ttyTHS0` 權限也要另外修正。

PX4 支援 MAVLink instance 使用 TELEM1/2/3、Ethernet等介面，Onboard profile 是 companion computer 的適當模式。[PX4 v1.15 MAVLink 參數](https://docs.px4.io/v1.15/en/advanced_config/parameter_reference)

## MAVROS 與 UXRE 差異

| 項目 | MAVROS／MAVLink | uXRCE-DDS |
|---|---|---|
| ROS 介面 | `/mavros/*` topics、services | `/fmu/in/*`、`/fmu/out/*` |
| 飛控介面 | MAVLink 標準訊息與 microservices | 直接橋接指定 uORB 訊息 |
| 版本耦合 | 較低；核心 MAVLink 訊息穩定 | `px4_msgs` 必須與韌體對齊 |
| 參數/任務 | 參數、任務、命令、FTP、GCS proxy 完整 | 主要針對即時 ROS 2/uORB |
| 即時資料 | 受 MAVLink stream profile/rate 限制 | 較接近 PX4 內部資料流 |
| 座標 | MAVROS自動轉換 ENU/FLU ↔ NED/FRD | 應用程式自行處理 NED/FRD |
| Offboard 心跳 | 持續傳送 MAVLink setpoint | `OffboardControlMode` 加 setpoint |
| 故障範圍 | MAVLink transport、Router、MAVROS plugin | Agent、DDS QoS、訊息版本、XRCE session |

MAVROS 支援 serial、UDP、TCP，並自動轉換 ROS 的 ENU/FLU 與 PX4 的 NED/FRD。[MAVROS ROS 2 README](https://github.com/mavlink/mavros/blob/ros2/mavros/README.md)

重要的是：MAVROS 自己的 MAVLink HEARTBEAT 不等於 Offboard proof-of-life。PX4 要求支援的 setpoint 持續高於 2 Hz，且進入 Offboard 前先維持至少一秒。[PX4 Offboard 說明](https://docs.px4.io/v1.15/zh/flight_modes/offboard)

## 兩組並行時的設定邊界

MAV 組禁止更動：

- `UXRCE_DDS_*`
- `SER_TEL2_BAUD`
- `/dev/ttyTHS1`
- `p450-micro-xrce-agent.service`

UXRE 組應避免更動：

- MAV 組最終選用的 `MAV_2_*`
- `SER_TEL3_BAUD`
- MAVROS service、TCP/UDP 14540/5760
- `/dev/ttyTHS0`

雙方共享、任何改動都必須重新同步：

- `COM_OF_LOSS_T`
- `COM_OBL_RC_ACT`
- RC loss、Kill Switch、arming、EKF/GPS 相關參數
- 飛控韌體與完整參數匯入
- 飛控重啟
- Offboard 模式與控制權

即使兩個 bridge 可以同時接收遙測，也不能同時執行控制 node。後續會讓所有 MAV 控制程式取得同一個控制鎖；UXRE 控制程式也應使用同一把鎖，避免兩邊同時送模式、解鎖或 setpoint。

## MAV 組實作計畫

1. 建立獨立 Git worktree/branch，避免兩個對話同時改 `main`。
2. 安裝並固定：

   - `ros-foxy-mavros=2.4.0`
   - `ros-foxy-mavros-msgs`
   - `ros-foxy-mavlink`
   - GeographicLib geoid dataset

   GeographicLib dataset 缺少時 MAVROS 會直接終止。[MAVROS 安裝說明](https://github.com/mavlink/mavros/blob/ros2/mavros/README.md#installation)

3. 先以 `pymavlink` 做 transport-only 測試，避免把線路問題誤判成 MAVROS 問題。
4. MAVROS 第一階段只接收遙測、讀參數，不送控制。
5. 驗證 `/mavros/state`、姿態、IMU、GPS、local position、battery、RC。
6. 無槳進行 setpoint continuity 測試，但不切模式、不解鎖。
7. 最後才測 OFFBOARD mode command、failsafe 與自動飛行流程。

本輪全程只讀，沒有修改 NX、PX4、Git 或 UXRE 設定。
